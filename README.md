# 协议号 频道 → 多群 转发（保留来源）

[![CI](https://github.com/niuma1337sys/telegram-/actions/workflows/ci.yml/badge.svg)](https://github.com/niuma1337sys/telegram-/actions/workflows/ci.yml)
[![License: AGPL-3.0](https://img.shields.io/badge/license-AGPL--3.0-blue.svg)](LICENSE)
[![Python](https://img.shields.io/badge/python-3.11%2B-blue.svg)](https://www.python.org/)
[![Tests](https://img.shields.io/badge/tests-347-brightgreen.svg)](#-跑测试)

用 **MTProto 协议号**（Telethon 用户号，不是 Bot）监听一个频道，把新消息转发到多个群。
采用 **forward 模式**：保留"转发自 XXX 频道"的来源标记，**不下载、不重传**，几乎不占带宽。

还能把**固定几条消息**长期反复发到多个群（定时重发），带网页面板和 Telegram 操控 Bot。

> 3. **默认配置是保守的**（间隔 3~6 秒、每分钟 20 条、每日 200 条），第一次别急着调高。

## 这个项目解决什么问题

频道 → 多群转发用 Bot API 做不到（Bot 读不到频道历史、不能监听任意频道），必须用协议号。
但自己写会踩一堆坑，这个项目逐条处理了：

| 坑 | 做法 |
|---|---|
| 断线重连后消息重复转发 | 去重记录落 SQLite，重放的消息直接丢弃 |
| 频道发一组图 → 被拆成 5 条、触发 5 倍风控 | 按 `grouped_id` 聚合，整组转发，只算 1 条配额 |
| 群开了慢速模式（如 30s）→ 每条都撞墙白等 | 发送前预判剩余窗口，等够了再发 |
| 被 FloodWait 罚站后越跑越慢 | 捕获后自适应降速（全局上限减半） |
| 一个群被限流 → 拖死其它群 | 每个目标独立队列、独立限速、独立退避 |
| 多群共享一个日额度 → 后面的群饿死 | 按群独立额度 + 全局总闸 |
| 账号被判定群发垃圾（PeerFlood） | 熔断：立刻停发并告警 |
| 进程活着但转发已经废了 | 健康巡检判断"业务健康"，不只是"进程在不在" |

```
源频道 ──▶ 监听(协议号) ──▶ 过滤 ──▶ 去重(落库) ──▶ 相册聚合
                                                      │
                                    ┌─────────────────┴─────────────────┐
                                    ▼                 ▼                 ▼
                              队列·群A          队列·群B          队列·群C
                            (独立限速/退避)   (独立限速/退避)   (独立限速/退避)
```

## 1. 快速开始

```bash
git clone <本仓库地址>
cd tg-relay

python -m venv .venv
# Linux/macOS
.venv/bin/pip install -r requirements.lock.txt
# Windows
.\.venv\Scripts\Activate.ps1; pip install -r requirements.lock.txt

cp .env.example .env      # 填 api_id / api_hash
$EDITOR config.yaml       # 填源频道和多个目标群

python -m tgrelay --login   # 首次登录：手机号 + 验证码（有二级密码会再问一次）
python -m tgrelay --check   # 自检：源/目标能否解析、有没有发言权限
python -m tgrelay --dry-run # 空跑：只打日志不真发，确认过滤规则挑对了消息
python -m tgrelay           # 正式运行（Ctrl+C 优雅退出）
```

> `requirements.lock.txt` 是锁定版本（34 个包），保证环境可复现；
> `requirements.txt` 是范围约束。生产部署建议用 lock 文件。

`api_id` / `api_hash` 在 <https://my.telegram.org/apps> 申请（**API development tools**）。

### 必须先做一次"暖场"

数字 ID（`-100...`）在协议号本地没有缓存时是**解析不出来**的，这是最常见的报错来源。
第一次运行前，用这个协议号在手机/桌面客户端里：

1. 加入源频道；
2. 加入每个目标群（**并在群里发过至少一条消息**，否则拿不到发言权限判定）；
3. 打开过每个会话。

程序启动时会自动 `get_dialogs()` 拉一次会话列表来灌缓存；如果 `--check` 仍报
`PeerIdInvalidError`，就是上面某一步没做，按提示先手动打开一次该会话。

## 2. 配置说明（`config.yaml`）

| 段 | 键 | 说明 |
|---|---|---|
| `sources` | 列表 | 源频道，可多个；`@用户名` 或 `-100...` 数字 ID |
| `targets` | 列表 | 目标群；每项可写 `id` / `interval`（单独限速）/ `label`（日志显示名）|
| `filters` | `keywords` | 命中任一关键词才转发；`keyword_mode: all` 则要求全部命中 |
| | `exclude` | 命中任一就跳过（优先级最高）|
| | `regex` | 正则白名单，命中任一才转发 |
| | `min_length` | **仅对纯文本**生效；带媒体的消息只看文案不受此限 |
| | `media` | 只转这些类型：`photo video document audio voice gif sticker poll` |
| `rate` | `per_target_interval` | **同一个群**两次发送的最小间隔（秒，区间内随机）|
| | `cross_target_delay` | 同一条消息投给多个群时，群与群之间的间隔 |
| | `global_per_minute` | 所有目标合计每分钟上限 |
| | `daily_cap` | 每日发送上限（按"帖子数"计，一个 5 张图的相册算 1 条）|
| `behavior` | `sync_edits` | 源消息被编辑时，同步编辑目标群里已转发的消息 |
| | `sync_deletes` | 源消息被删除时，同步删除目标群里的转发 |
| | `catch_up_on_start` | 启动时补齐离线期间漏掉的消息（按 msg_id 增量拉取）|
| | `album_window` | 相册聚合窗口（秒），网络慢可以调到 1.0 |
| | `queue_size` | 每个目标的待发队列长度，满则丢弃并告警 |
| `premium` | | `true` 时全局上限和日上限自动放大 4 倍（见下）|

### 关于"另一个号充会员"

代码把 Premium 做成了一等公民：

* `.env` 里把 `TG_PREMIUM=true`（或 `config.yaml` 的 `premium: true`，或命令行 `--premium true`）即可，
  **不用改代码**：全局每分钟上限和日上限自动 ×4。
* 会员的实际收益不止配速：**非会员无法转发开启"禁止转发"保护的频道内容**，
  会员可以。遇到 `ChatForwardsRestrictedError` 时，日志会直接给出这条提示。
* 一个号既监听又发送完全够用（转发不需要下载重传）。
  以后想拆成"1 个监听号 + N 个发送号"，只需在 `sender.py` 里换 client 实例，其余逻辑不用动。

## 3. 运行行为（踩过的坑都在这里）

| 场景 | 处理方式 |
|---|---|
| 断线重连后 Telegram 重放旧更新 | 去重记录**落 SQLite**（`seen` 表主键 `源+消息ID`），重放的消息直接丢弃 |
| 频道发一组图（相册） | 按 `grouped_id` 聚合后**整组转发**，保持图集形态，只消耗 1 次配额 |
| 相册被拆散/超 10 张 | 超过 Telegram 单组上限的自动截断并告警 |
| 某个群队列积压 | 该群独立队列满后**丢弃并告警**，绝不阻塞监听（否则会丢更新）|
| `FloodWaitError` | 等够时间后重试，并**自适应降速**（全局上限减半）；超过 15 分钟则放弃该条 |
| `SlowModeWaitError` | 遵守群里的慢速模式 |
| `PeerFloodError` | **熔断**：立即停止全部发送并告警——再发就会被限制/封号 |
| 没权限/被封/ID 无效 | 标记为永久失败，暂停该目标，**其它群不受影响** |
| 今日配额用完 | 记录为 `skipped`，不再发送（跨重启累计）|
| 启动时补齐漏掉的消息 | `catch_up_on_start`，从游标 `last_msg_id` 往后拉取 |
| Ctrl+C | 先把相册缓冲冲刷完，再停 worker，最后打印统计 |

## 4. 上线节奏（重要）

单号转发是 Telegram 重点监控的行为，**不要一上来就跑满**：

1. `--dry-run` 跑 10 分钟，确认过滤规则挑出来的正是你想转的消息；
2. 只留 1 个目标群，正式跑 30 分钟，看日志有没有 `FloodWait`；
3. 加满目标群，按 `per_target_interval: [3, 6]`、`global_per_minute: 20`、`daily_cap: 200` 观察 24 小时；
4. 24 小时无 FloodWait 再逐步放宽（比如间隔降到 `[2, 4]`）。有 FloodWait 就退回上一档。

日志里每 5 分钟会打一次汇总，出现 `目标积压` 或 `熔断状态` 要立刻处理。

## 7. 目标群开了慢速模式怎么配

群设置的慢速模式（如 **30 秒**）是**群强制的**，比任何本地限速都硬：

| 慢速设置 | 实际吞吐上限 | 一天最多 |
|---|---|---|
| 10s | 6 条/分钟 | 8640 条 |
| 30s | 2 条/分钟 | 2880 条 |
| 60s | 1 条/分钟 | 1440 条 |

程序的处理方式（`SlowModeGuard`）：

1. **启动时 `--check` 会打印该群的真实慢速设置**，并按它核对你的配置；
2. **发送前预判等待**——记住"下次可发送时刻"，到点再发，不去撞墙。
   撞墙的代价是整个窗口白费（网络上很多脚本就是这样越跑越慢的）；
3. 撞上时兜底等待并重试，**不消耗发送尝试额度**（否则一次慢速模式就能把消息丢掉）；
4. 剩余等待超过 180 秒（比如 15 分钟慢速），本条记为 `skipped` 跳过，
   **不算失败、不暂停目标**，下一条继续；
5. 窗口过期自动清空，避免一条错误的估计把之后所有消息无限延后。

**建议把该目标的 `interval` 对齐到慢速值**（例如 `interval: [30, 35]`），
两边一致时节奏最稳。

**积压是慢速模式下的主要矛盾**。30 秒一条意味着队列最多缓冲
`queue_size × 30s`（默认 200 条 ≈ 100 分钟）。源连续刷屏超过这个时长时，
队列满会**丢弃最旧的那条、保留最新的**——保新弃旧对读者更合理。
日志里会打印累计丢弃数（每 25 条一次，不刷屏）和 `peak_backlog`。

## 8. 定时重发（把固定几条消息反复发到群里）

如果你要的不是"源发什么就转什么"，而是"把固定的几条内容长期摆在群里"，用 `repost` 段。
它和实时转发是**两套独立逻辑**，可以同时开，也可以只开一个。

```yaml
repost:
  enabled: true
  ranges:
    - "6-10"        # 第 6 条到第 10 条（含两端），从 t.me/example_channel/6 开始的一段
  ids: [15, 20]     # 再补几条离散的，与 ranges 合并去重（只放单条，区间写 ranges）
  interval: 300     # 每轮间隔（秒）
  daily_limit: 200  # 重发单独的每日额度，不挤占 rate.daily_cap
  targets: []       # 留空 = 所有 targets
  shuffle: false    # true = 每轮随机顺序
  run_mode: loop    # loop 常驻 / once 只跑一轮
```

```powershell
python -m tgrelay --repost-only        # 只做定时重发，不启动实时转发
python -m tgrelay --repost             # 实时转发 + 定时重发 同时跑
python -m tgrelay --repost-once        # 只跑一轮，验证素材对不对
```

**间隔怎么算**（重要）：一轮要把**每条素材都发一遍**，所以
`一轮耗时 ≈ 素材数 × 群慢速`。5 条素材 + 30s 慢速 = 150 秒，
`interval` 至少要大于它，否则就会一轮接一轮不停发。配置示例给了 300 秒。

> ⚠️ **真正决定"一小时发几条"的不是 `repost.interval`，而是 `targets[].interval`。**
> 素材变成 N 条之后，每轮要发 N 条，一轮的花费时间就是 `N × 群发送间隔`；
> `repost.interval` 只是"一轮跑完之后再等多久"。所以想要"每个群最多 5 分钟一条"，
> 就该把 `targets[].interval` 设成 `[300, 300]` —— 这个限制和你有几种素材无关。
> （真实事故：素材 1 条、群间隔 30s，5.5 小时发了 230 条同样的内容，账号被 Telegram 限制。）

程序会在启动时直接**拦下**这些配错的情况，不会带着错误配置跑：

| 配错 | 后果 | 程序行为 |
|---|---|---|
| `interval` < 31 秒 | 每条都撞慢速墙、白等 | 启动即报错，并告诉你该设多少 |
| `daily_limit` 超过慢速理论上限 | 配额永远用不完 | 启动即报错 |
| `ids` 里写了区间 | 语义不清 | 报错并提示改用 `ranges` |
| `run_mode` 拼错 | 行为不确定 | 报错 |

**两本配额账**：`rate.daily_cap`（实时转发）和 `repost.daily_limit`（重发）分开记，
互相不挤占。日志里能看到四个数：`额度占用` 和 `实发` 各两个。

> 为什么"额度占用"会大于"实发"？额度是在**发送前**预占的（防止重试无限消耗配额），
> 所以被跳过的那几次也占用了额度。**永久失败（发不出去）的那次会把占位退回来** ——
> 根本没送到群里的消息不该继续占着当天配额，否则一个被封的目标会把配额整个吃光。
> 对外报数看 `实发` 那两项。

**素材被删了怎么办**：启动时按 ID 拉取，取不到的消息会打警告并跳过；
运行中如果某条素材在源里被删除，会记一次永久失败并跳过该目标，其它素材照常。

## 9. 常见问题

**Q：`--check` 报 `PeerIdInvalidError` / `无法解析`**
按第 1 节做暖场；确认 ID 是 `-100` 开头的完整群 ID（用 `@username` 最省事）。

**Q：日志里出现"目标已暂停接收新任务"**
那个目标遇到了永久性错误（无权限/被封/禁转），打开日志看具体原因，修好后重启程序即可恢复。

**Q：转过去的消息没有"转发自 XXX"标记吗？**
有。本项目用的是 `forward_messages`，来源标记一定保留（这正是你选 forward 模式的原因）。

**Q：想改成"去转发头"（看起来像原创）？**
需要改成复制模式：把 `_forward()` 里的 `forward_messages` 换成下载再 `send_file/send_message`，
代价是耗带宽、大文件慢、投票/位置等特殊消息会失真。当前设计没有走这条路。

**Q：账号会不会被封？**
MTProto 用户号群发确实有风险，所以本项目把限速做成一层层硬约束（同群间隔、跨群间隔、全局每分钟、日上限、FloodWait 自适应降速、PeerFlood 熔断）。
按第 4 节的节奏从保守值起步、别用新号高频群发，是能长期稳定跑的。

最容易被忽视的一条：**反垃圾系统最在意的是"同一个群里反复发同样的内容"**，
而不是总发送量。5 小时往同一个群发 200 多条一模一样的内容，比一天往 20 个群
各发 10 条更容易触发限制。素材尽量多准备几条并开 `shuffle`。

程序内置了一道**发送节奏体检**（`tgrelay/risk.py`），会在启动日志、`/status`
和网页面板上点名警告这些配法（只警告、不阻止）：

| 检查项 | 阈值 |
| --- | --- |
| 群发送间隔（`targets[].interval`） | ≤ 60s 高危，< 120s 提醒 —— 它才是真正的节流阀 |
| 素材条数 | < 5 条提醒（1 条高危） |
| `shuffle` | 多素材却没开 → 提醒 |
| 单群日发送量 | > 60 条提醒，> 120 条高危 |
| 单素材日重复次数 | > 30 次提醒 |

**Q：怎么知道号被 Telegram 限制了？**
群权限里**看不出来**——被限制时 `channels.GetParticipant` 依然显示"普通成员、可发言"，
被动自检也会一路报 OK。只有两个办法：

```bash
python -m tgrelay --check-account    # 问 @SpamBot（会真的发一条 /start）
python -m tgrelay --probe-send       # 真发一条，看 Telegram 收不收（会往群里发东西）
```

程序内置了自动刹车：单个目标报"禁止发言"→ 停发该目标 30 分钟；
**两个以上目标在 15 分钟内都报 → 判定账号级限制，直接熔断并给操控 Bot 发告警**
（只配了一个群时，会主动问一次 @SpamBot 来确认）。熔断之后所有发送直接跳过，
连 API 都不碰。

**Q：被限制了怎么办？**
用登录该号的手机/桌面端打开 **@SpamBot** → `/start` → 点 "This is a mistake" 申诉，
然后**等**（常见 1 天到 1 周，没有官方保证）。期间别再用这个号发东西，继续发只会加重处罚。
解除后用 `/account`（Bot）或面板「账号自检」确认，再 `/repost on` 恢复发送。

**Q：能不能再加一个账号？**
**当前不支持，是单账号架构。** 要加需要改：账号表 + 发送账号池 + 按账号限流 +
账号分配策略，约 1~2 天工作量。群数 ≤ 10 时单账号够用；
再多会需要账号池（因为一个号的日发送量有硬上限）。

**Q：一个号被限制/封了怎么办？**
分三种：会话失效（重新 `login.py` 登录，要验证码）／被限流或反垃圾限制（停发等解除，
见上面两条）／号真的废了（换号，新号必须加源 + 加所有目标群 +
在每个群里发过消息）。**换号后不会重复转发**（去重表按源记，与账号无关）。

**Q：怎么远程管理？**
两种：`--bot` 起一个 Telegram 操控 Bot（31 个命令，BotFather 菜单里放 29 个，手机随时可用），
或 `--web` 起网页面板（表格化批量管理）。
**两者都跑在同一个进程里**——同一个 session 不能被两个进程持有。
